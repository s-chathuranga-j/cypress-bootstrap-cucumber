# Explaining, Reviewing, And Debugging Tests

Use this reference when the user asks how a test works, why it failed, whether it is flaky, or for a review without necessarily requesting code edits.

## Classify The Question

- Cypress concept/API question: explain the purpose, mental model, smallest useful example, common uses, and pitfalls.
- Specific feature/step failure: read the feature, step file, page object/API client, support file, and config needed to understand it.
- Review request: prioritize risks, regressions, flakiness, missing assertions, and framework violations.

Prefer authoritative Cypress docs or `npx cypress --help` before making API claims.

## Explain A Test

Keep explanations concise and organized around:

1. Intent: what behavior or contract the scenario verifies.
2. Structure: setup, action, assertion, and cleanup/state handling.
3. Cypress mechanics: command queue, retryable assertions, intercepts, subjects, sessions, and custom commands.
4. Dependencies: data, app state, environment variables, API server, BrowserStack credentials, page object selectors.
5. Risks: timing, brittle selectors, duplicate steps, hidden state coupling, weak assertions, UI-only setup, or generated reports/secrets.

## Review Or Debug A Test

Look for these problems first:

- Direct selectors in step definitions instead of page objects.
- Duplicate Cucumber step text across files.
- `.spec.ts` or `.cy.ts` files added instead of framework `.feature` + `.steps.ts` pairs.
- Arbitrary waits, manual Promise control, `async`/`await` mixed with `cy.*`, or command results stored in outer variables.
- Scenarios that depend on previous scenarios or shared mutated state.
- UI setup where API/client setup would be more deterministic.
- Missing explicit assertions after actions.
- Weak selectors in page objects: classes, DOM depth, autogenerated IDs, element order.
- Intercepts defined after the triggering action.
- Secrets or generated files committed into source.

## When A Test Fails

Triage in this order:

1. Confirm the right tag/spec/feature ran.
2. Check environment values and local service availability (`API_BASE_URL`, port `3100`, BrowserStack env vars).
3. Read the failing step and the page object/API client it calls.
4. Identify whether failure is app behavior, test data/state, selector drift, timing/network, or framework configuration.
5. Prefer a deterministic fix over increasing timeouts.

## Suggested Output Shape

- Start with the finding or explanation, not a long preamble.
- Use file references when reviewing local code.
- Mention assumptions and residual risk.
- If proposing fixes, keep them aligned with this framework's POM, Cucumber, API-client, and tag conventions.
